# План разработки: универсальный мониторинг объявлений (Kufar) с фильтрами и уведомлениями в Telegram

**Цель:** универсальная система мониторинга объявлений на **Kufar**. Пользователь задаёт **объекты мониторинга** («таргеты») — любые позиции (коньки, велосипед, диван, iPhone…) — с произвольным набором фильтров: поисковый запрос, города, цена, ключевые слова, числовые параметры (размер, объём, мощность и т.п.). При появлении подходящих объявлений система уведомляет в Telegram.

> Onliner (Барахолка) сознательно **не используется** — его поиск требует HTML-скрейпинга без структурированных данных. Исследование сохранено ниже как справочный материал на будущее. Архитектура (единая модель + правило-движок) позволяет добавить площадку без переделки логики фильтров.

---

## 1. Требования (acceptance criteria)

- [ ] Отслеживает **Kufar**.
- [ ] **Несколько таргетов** одновременно: у каждого — свой запрос, города, фильтры.
- [ ] Таргеты задаются в `config.yaml` **и** управляются командами Telegram-бота (без правки кода).
- [ ] Универсальные фильтры для любого таргета:
  - [ ] поисковый запрос + категория Kufar (опционально);
  - [ ] города: Гомель, Минск и другие (любой `rgn`/`ar`);
  - [ ] диапазон **цены** (мин/макс) — опционально, по умолчанию без ограничений;
  - [ ] **ключевые слова** (обязательные: бренд и т.п.) и **исключения** (антимусор);
  - [ ] **числовые параметры** через код параметра Kufar (для коньков — размер `sports_shoes_size`, для велосипедов — `bike_wheel_size` и т.д.).
- [ ] При появлении подходящего объявления — сообщение в Telegram со ссылкой, ценой, ключевыми параметрами, городом и фото.
- [ ] Нет дублей уведомлений (дедупликация).
- [ ] Работает автономно по расписанию (каждые 5–15 минут).

## 2. Результаты исследования площадки (проверено вживую)

### Kufar — есть удобный JSON API ✅
`GET https://api.kufar.by/search-api/v2/search/rendered-paginated`

Параметры запроса (проверено):
- `query` — поисковый запрос (например, «коньки»)
- `cat` — категория (опционально)
- `rgn` — регион: 1 Брестская, **2 Гомельская**, 3 Гродненская, 4 Могилёвская, 5 Минская область, 6 Витебская, **7 = Минск (отдельный регион!)**
- `ar` — город (район): **Гомель = ar=5** (проверено). Для Минска `ar` — это район города (Московский, Центральный…), поэтому Минск задаётся просто `rgn=7` без `ar`
- `size` — число результатов на страницу, `page` — пагинация

В ответе по каждому объявлению:
- `ad_id`, `ad_link` (https://www.kufar.by/item/…)
- `subject` — заголовок
- `price_byn` + `price_usd` / `price_eur` — цена
- `ad_parameters` — **структурированные параметры**: каждый вида `{pl: "Название", p: "код", v: значение, vl: "текст"}`, например размер (`sports_shoes_size`), состояние (`condition`), регион (`region`), город (`area`)
- `images` — ссылки на фото

**Ключевой момент для универсальности:** фильтрация по любому параметру строится на кодах `p` из `ad_parameters`, а не на хардкоде под коньки. Коды параметров зависят от категории — их можно подсмотреть, сделав пробный запрос по категории (на этапе 1 сделаем утилиту-помощник).

### Onliner (Барахолка) — НЕ ИСПОЛЬЗУЕТСЯ (справка на будущее) 📌
Причины отказа: поиск только через HTML-скрейпинг (`search.php?q=…`, ~25 результатов на страницу), нет структурированных параметров (размера и т.п.), JSON-API `api/search/topics` не фильтрует по запросу, региональная фильтрация требует реверс-инжиниринга, поиск ловит мусор. Если захотим добавить — понадобится фетчер-адаптер, остальной код (правила, dedup, уведомления) менять не нужно.

## 3. Архитектура

```
Scheduler (каждые 5–15 мин)
   │
   ├── Fetcher: Kufar (REST JSON)  ← query, cat, rgn, ar из таргета
   │
   ├── Normalizer → модель Ad (source, url, title, price, city, params: {код: значение}, images)
   │
   ├── Rule Engine: проверка Ad против таргета (цена, слова, исключения, параметры, город)
   │
   ├── Store (SQLite: seen_ads, targets, subscribers)
   │
   └── Notifier → Telegram Bot API (сообщение с фото + ссылкой)
```

- **Таргет** — декларативное описание «что ищем», живёт в `config.yaml` и/или в БД (создаётся через бота).
- **Правило-движок** — единая универсальная проверка: не важно, коньки это или iPhone, логика фильтрации одна.
- **Фетчер изолирован**: новая площадка = новый адаптер, который отдаёт ту же модель `Ad`.

## 6. Модель таргета и правило-движок (ядро универсальности)

### Таргет — `config.yaml`

```yaml
targets:
  - name: "Фигурные коньки Graf / Edea / Risport 37"
    query: "коньки"
    category: 4020              # Спорттовары (опционально, можно найти через утилиту)
    regions:
      - { rgn: 2, ar: 5, label: "Гомель" }   # Гомельская обл. / Гомель
      - { rgn: 7, label: "Минск" }            # Минск — отдельный регион (rgn=7)
    must_contain: [graf, edea, risport]  # бренды (OR; для AND — флаг all: true)
    must_not_contain: [хоккейн, детск, "конек кровельн"]  # антимусор
    params:                     # фильтр по структурированным параметрам Kufar
      sports_shoes_size:        # код параметра из ad_parameters
        min: 37
        max: 37
```

Тот же формат используется при создании таргета через бота (команда `/add`).

### Семантика правил

| Правило | Логика |
|---|---|
| `price` | число в диапазоне (мин/макс, по `price_byn`) |
| `must_contain` | подстрока без учёта регистра в заголовке; OR по умолчанию, `all: true` — AND |
| `must_not_contain` | если любое слово найдено — отсев (AND-исключение) |
| `params.<код>` | значение из `ad_parameters[код]`; `[список]` — точные значения, `{min,max}` — числовой диапазон |
| `regions` | запрос к API идёт с `rgn/ar` таргета + контроль по кодам `region`/`area` из ответа (для Минска `area` — район города, поэтому сравниваем коды, а не текст) |

### Нормализация значений
- Цены приводятся к BYN (`price_byn`).
- Числовые параметры (размер и т.п.): чистка текста → число. Для размеров обуви (EU/US/CM) — встроенная таблица конвертации, подключаемая по имени параметра (`size_table: shoes` в таргете, опционально).

## 7. Хранение (SQLite)

- `seen_ads(ad_id, url UNIQUE, title, price, params_json, city, first_seen, last_seen, notified_at)` — дедупликация; уведомляем только новые.
- `targets(id, name, config_json, active, created_at)` — таргеты, созданные через бота; конфиг сериализован в JSON.
- `subscribers(chat_id, active)` — кто получает уведомления.
- `price_history(ad_id, price, ts)` — опционально, для «снизили цену».

Порядок приоритета таргетов: из БД (динамические) + из `config.yaml` (статичные). При старте и после каждого изменения через бота — пересборка списка.

## 8. Telegram-уведомления и управление

Сообщение о находке:
```
🔔 [Имя таргета]
🏒 Bauer Vapor X2.7 — 250 BYN
📍 Гомель · 🛒 Kufar · ⏱ 2 ч. назад
📏 Размер: 42
🔗 https://www.kufar.by/item/…
[фото объявления]
```

Команды бота:
- `/start` — справка + подписка на уведомления
- `/subscribe`, `/unsubscribe` — вкл/выкл уведомления
- `/add` — пошаговое создание таргета (имя → запрос → города → цена → слова → параметры)
- `/list` — список таргетов с активностью и количеством найденного
- `/remove N` — удалить таргет (только созданный через бота)
- `/status` — время последнего скана, ошибки фетчеров
- `/last N` — последние N найденных объявлений

## 9. Расписание и вежливый скрейпинг

- Интервал **5–15 минут** + случайный сдвиг.
- На каждый таргет — **свой запрос** к Kufar (query + регионы). Один запрос на регион за цикл; при необходимости пагинация с задержкой.
- Кэш ответов за цикл: одно и то же объявление, подходящее под несколько таргетов, не скачиваем повторно.
- Правильный `User-Agent`, таймауты, ретраи с экспоненциальным backoff, обработка HTTP 429/5xx.
- Логирование в файл (`logs/`), алерт в Telegram при падении фетчера.

## 10. Docker: образ и запуск через compose

### Dockerfile
- Базовый образ `python:3.11-slim` (лёгкий, безопасный).
- Установка зависимостей из `requirements.txt` отдельным слоем (кэширование при сборке).
- Копирование исходников, запуск от **не-root** пользователя.
- `HEALTHCHECK` — лёгкая проверка (процесс жив, БД доступна).
- `CMD ["python", "main.py"]`.

### docker-compose.yml
```yaml
services:
  wishsale:
    build: .
    image: wishsale:latest
    restart: unless-stopped          # автоподъём после падения/перезагрузки сервера
    env_file: .env                   # BOT_TOKEN и пр. — секреты не в образе
    environment:
      - TZ=Europe/Minsk              # корректные временные метки
    volumes:
      - ./data:/app/data             # SQLite и логи переживают пересоздание контейнера
      - ./config.yaml:/app/config.yaml:ro
    healthcheck:
      test: ["CMD", "python", "-c", "import sqlite3; sqlite3.connect('/app/data/wishsale.db')"]
      interval: 1m
      timeout: 5s
      retries: 3
```

### Жизненный цикл
- Сборка и запуск: `docker compose up -d --build`
- Логи: `docker compose logs -f wishsale`
- Обновление после правок: `docker compose up -d --build` (данные сохраняются в `./data`)
- Остановка: `docker compose down`

### Важные решения
- **Том `./data`** — SQLite и логи на хосте: контейнер можно пересоздать/обновить без потери состояния.
- **`.env` через `env_file`** — токен не попадает в образ и в git.
- **`restart: unless-stopped`** — самовосстановление после сбоев и перезагрузки машины.
- **`config.yaml` монтируется read-only** — правки конфига не требуют пересборки образа.
- Образ собирается один раз и одинаково работает на любой машине с Docker (мак/VPS).

## 12. Риски и как с ними справляемся

| Риск | Митигация |
|---|---|
| Kufar меняет API | фетчер изолирован; при поломке — уведомление в Telegram, быстрый фикс |
| Антибот-блокировки | низкая частота запросов, корректный UA, случайные интервалы |
| Коды параметров зависят от категории | утилита-помощник подсматривает коды пробным запросом; коды хранятся в таргете |
| Мусорные результаты поиска | `must_contain` (бренд) + `must_not_contain` в каждом таргете |
| Пользователь задал неверный параметр/код | валидация при `/add`, подсказка доступных кодов |
| Размеры в разных системах (EU/US/CM) | опциональная таблица конвертации по имени параметра |
| Сборка/запуск Docker на машине | проверяется на этапе 4 локально (мак) и на VPS; том `./data` сохраняет состояние |
| Юридические/этические | только публичные данные, низкая частота, не храним личные данные продавцов |
| **Telegram API заблокирован в РБ** | запуск на VPS вне Беларуси (Docker) или `HTTPS_PROXY` в `.env` — `requests` использует прокси автоматически |

## 13. Тест-план (приёмка)

1. Таргет «Фигурные коньки Graf / Edea / Risport, размер 37, Гомель и Минск» (`query: "коньки"`, `must_contain: [graf, edea, risport]`, `params: { sports_shoes_size: [37] }`) → подходящее объявление даёт уведомление за ≤ 15 минут. *(при живой проверке: найдены RISPORT RF 3 PRO и EDEA 37 в Минске)*
2. Неподходящий бренд (например, Bauer/CCM — хоккейные), размер (36 или 38) или город (Витебск) → уведомления нет.
3. «Конек кровельный» и прочий мусор → отфильтрован через `must_not_contain`.
4. Запустить два цикла подряд → дублей нет.
5. Добавить таргет через `/add` (например, «фигурные коньки, размер 35») → работает без перезапуска.
6. `/list`, `/remove`, `/status` работают корректно.
7. Выключить интернет на 5 минут → бот переживает, при восстановлении продолжает работу.
8. Одно объявление под несколько таргетов → уведомление по каждому таргету (или один раз — по настройке), без повторных HTTP-запросов.
9. **Docker**: `docker compose up -d --build` собирается и запускается; после `docker compose down && up` — таргеты и история объявлений на месте (том `./data`).
10. **Docker**: `docker compose restart` — бот продолжает работу и уведомляет без потери данных.
